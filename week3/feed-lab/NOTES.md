# 발표자 메모 (90분)

## 시작 전

1. `make up` (캐시 예열 포함) → `make check` 로 수치 점검 (3분). 전부 PASS 인지 확인. 끝나면 자동으로 초기화된다.
2. 브라우저 전체 화면(⌃⌘F), 기록표 `지우기`, 버전 v1, 부하 `정지`, 계정 A.
3. 화면 공유나 Zoom 을 켠 상태로 한 번 더 `읽기 300` 을 눌러 숫자가 비슷한지 본다 (CPU 를 나눠 쓰기 때문).
4. 단축키: `1`~`4` 버전, `M` 지표 크게(상황판만 화면 가득. 이 모드에서는 버튼이 안 보이므로 `Q` C 셀럽 글, `W` D 글, `E` 셀럽 5명, `R` 셀럽 5명 → D 글 을 키로 누른다), `C` 코드, `Esc` 코드 닫기.

주의
- **v1 에서는 쓰기 부하를 걸지 않는다.** v1 의 쓰기는 feeds 에 반영되지 않아서 v2 로 넘어가면 그 글이 안 보인다. (프리셋도 그렇게 짜여 있다. `읽기 300 + 쓰기 5` 는 v2 부터)
- v1 포화 중에 `새로고침` 을 누르면 대부분 3초쯤 걸리거나 503 이지만, 가끔 운 좋게 바로 커넥션을 잡아 빨리 올 때가 있다. 한 번 더 누르면 된다. (커넥션 풀이 엄격한 선착순이 아니라서 생기는 일. 질문이 나오면 그대로 설명)
- 버전을 바꾼 직후 3~8초는 앞 버전에서 밀린 요청이 빠지는 시간이다. p99 카드는 최근 5초 기준이라 조금 늦게 떨어진다. 기다리면서 "밀린 줄이 빠지고 있다"고 말하면 된다.

장표는 `slides/index.html` (33장 + 부록 2장 + 배경지식 3장, 그중 어두운 4장이 '시연으로 넘어가라'는 표시). 버전마다 문제 상황 → 개선 애니메이션 → 설명 → 구조 → 시연 → 결과 순서다. 장표마다 `N` 키로 이 메모의 요약이 뜬다.

## v1 읽을 때 모은다

1. `읽기 30`. 산점도가 **오른쪽 위로 곧게** 올라간다. 코호트 표: 라이트 4ms / 미드 11 / 헤비 55.
   - "비용이 뭐에 비례하죠?" → 내가 팔로우한 사람 수.
2. 계정 A 새로고침 50ms, B 로 바꿔서 4ms. `C` 눌러 코드: LATERAL 안쪽이 **팔로우한 사람 수만큼** 돈다.
   터미널 `make explain`: `loops=3000`, `rows=60000`, 버퍼 69,287 대 468.
3. `읽기 300`. 5초 안에: DB 풀 20칸 전부 빨강 + 대기 880, p99 3.8초, 성공 120/300, 에러 60%.
   - **산점도가 평평해진다.** 라이트 유저도 3초. "헤비 유저 몇 명 때문에 모두가 느려진다. 같은 줄에 서 있으니까."
   - 관찰자 패널도 `읽기 실패 (503)`. 내 피드 새로고침도 3초 또는 실패.
4. `헤비만 300` → 성공 47/300. 천장은 "요청 수"가 아니라 "요청이 시키는 일의 양"이 정한다.
5. 던질 질문: "결과를 캐시하면?" → "누가 글을 쓰면 그 사람 팔로워 전원의 캐시가 틀려진다" → "그럼 글 쓸 때 미리 만들어 두면?" → v2.

DB 를 CPU 2개로 묶어 둔 이유를 물으면: 노트북 DB 는 12코어를 다 쓰면 700rps 까지 받는다. 시연용으로 천장을 낮춘 것이고, 실서비스에서는 천장이 더 높은 곳에 있을 뿐 모양은 같다.

## v2 쓸 때 뿌린다

1. 부하를 끄지 말고 `2`. 밀린 줄이 빠지고 나면 p99 3ms, 성공 300/300, 산점도가 **바닥에 평평**. `읽기 3000` 도 3000/3000 (5,000rps 까지도 p99 2ms 로 받는다. v1 의 천장은 120rps 였다).
2. `C` 코드: 읽기는 `feeds` 에서 20줄. 쓰기는 `fanout.deliver(post)`, Fanout.kt 탭에서 팔로워 수만큼 INSERT.
3. `읽기 300 + 쓰기 5`. 오른쪽 산점도(쓰기)가 이번엔 **팔로워 수에 비례**해서 올라간다. 일반 쓰기 평균 80ms.
4. `C 셀럽 글 쓰기` → 토스트 **5초**, 쓰기 카드 빨강, feeds +50,000 이 올라가는 게 보인다. 관찰자 배지 `도착까지 5.5초`.
   - "우리 셀럽은 5만 명인데 5초. 팔로워 1,000만이면?" (1,000초)
5. 질문: "이 테이블 1년 뒤엔?" (지금도 3일치가 2,200만 행 2.6GB. 그래서 실서비스는 유저당 최근 수백 개만 남기고, 휴면 유저에게는 안 뿌린다)

**"배치로 묶으면 빨라지지 않나요?"** 가 나오면: 설정에서 묶음 크기를 1000 으로 바꾸고 셀럽 글을 다시 쓴다 → 0.35초. 빨라지지만 팔로워 수에 비례하는 건 그대로다.
그리고 실서비스의 피드는 유저마다 다른 샤드나 캐시 키에 있어서 한 테이블에 묶어 넣듯이 되지 않는다. 팔로워 한 명당 한 번 쓰는 기본값이 오히려 현실에 가깝다. 끝나면 1 로 되돌린다.

## v3 나중에 뿌린다 (아웃박스)

1. `3`. `C 셀럽 글 쓰기` → 토스트 **3ms**. 반영 지연 카드가 올라가다가 관찰자 배지 `도착까지 5.9초`.
   - "응답은 빨라졌는데 일은 그대로다. 요청 밖으로 옮겼을 뿐."
2. `C` 코드: `posts` INSERT 와 `fanout_jobs` INSERT 가 **같은 `@Transactional`** 안에 있다.
   - 왜 같은 트랜잭션? 글만 저장되고 잡이 빠지면 그 글은 영원히 아무 피드에도 안 뜬다. 둘 다 남거나 둘 다 안 남아야 한다.
   - 워커: `@Scheduled(fixedDelay)`. 앞 실행이 끝나야 다음이 시작되므로 겹침 방지가 따로 필요 없다.
   - 워커가 도중에 죽어서 같은 잡을 다시 돌려도 `PRIMARY KEY (user_id, post_id)` + `ON CONFLICT DO NOTHING` 이라 중복이 안 생긴다 (멱등).
3. `셀럽 5명 → 1초 뒤 D 글`. 큐 대기가 40~50건까지 쌓이고(부하가 쓴 평범한 글들), 반영 지연 카드가 빨갛게 20초까지 올라간다.
   관찰자 패널에 셀럽 글이 6초, 10초, 14초, 17초, 20초에 하나씩 뜨고 **D 글은 20초 뒤에** 뜬다.
   - "D 는 팔로워가 200명이다. 0.02초면 끝날 일인데 셀럽 뒤에 서서 20초를 기다렸다." (head-of-line blocking)
4. 질문: "스프링 이벤트(@Async)로 했으면?" (서버가 죽으면 메모리의 할 일이 사라진다. 잡을 DB 에 남긴 이유)
   / "워커를 여러 개 돌리면?" (`FOR UPDATE SKIP LOCKED` 로 가능. 하지만 셀럽 5명이 워커 5개를 다 잡으면 똑같다) / "즉시 반영이 요구사항이면?"

## v4 셀럽만 따로 (하이브리드)

1. `4`. 같은 버튼 `셀럽 5명 → 1초 뒤 D 글`. 셀럽 글 1초, **D 글 0.5~1초**. 큐가 쌓이지 않는다.
2. `C` 코드: 워커는 `strategy == "hybrid" && isCeleb` 이면 건너뛴다. 읽기는 `feeds` + 내가 팔로우한 셀럽 글을 v1 과 같은 쿼리로 가져와 합친다.
   - v1 의 쿼리가 돌아왔다. 다만 대상이 "내가 팔로우한 3,000명"이 아니라 "그중 셀럽 몇 명"이다.
3. 읽기 p99 가 2ms → 3ms 로 **조금 올랐다**는 걸 짚는다. 비용이 또 옮겨갔다.
4. 질문: "기준을 몇 명으로?" → 설정에서 40000 으로 바꾸면 셀럽이 2명으로 줄고, 나머지 3명의 잡이 다시 큐를 막는다 (D 글 도착 10.7초).
   1000 으로 내리면 셀럽이 480명이 되고 헤비 유저의 읽기 p99 가 3ms → 4ms 로 오른다. 이 규모에선 작지만 방향은 같다. 정답은 없고 재 보고 정한다. 끝나면 10000 으로 되돌린다.

## 마무리

기록표를 읽는다. 빨간 칸이 v1 은 읽기, v2 는 셀럽 쓰기, v3 는 D 글 도착에 있고 v4 에서 전부 초록이 된다. 대신 v4 는 코드가 가장 복잡하고 읽기가 약간 비싸다.

| | 읽기 | 쓰기 | 반영 | 복잡도 |
|---|---|---|---|---|
| v1 | ∝ 팔로우 수 | 최소 | 즉시 | 낮음 |
| v2 | 최소 | ∝ 팔로워 수 | 응답과 동시 | 중간 |
| v3 | 최소 | 최소 | 지연, 셀럽 뒤에 막힘 | 높음 (워커, 멱등, 모니터링) |
| v4 | 조금 증가 | 최소 | 1초 안팎 | 가장 높음 |

티저: "글마다 좋아요 수를 같이 보여 주려면?" (읽을 때 세면 v1 문제, 쓸 때 올리면 핫 로우 경합)

## 왜 이렇게 만들었나 (질문 대비)

- **open-loop 부하**: 응답을 기다렸다가 다음 요청을 보내면 서버가 느려질수록 부하도 줄어 천장이 안 보인다. 목표 rps 대로 그냥 쏜다.
- **커넥션 3초 타임아웃**: 못 얻으면 503. 줄이 무한히 길어지지 않아 버전 전환이 몇 초 안에 끝나고, 포화가 에러율로도 드러난다.
- **풀을 둘로 나눔**: 피드/작성은 `main`(20), 워커와 메트릭과 화면 보조 API 는 `ops`(6). v1 이 포화돼도 상황판은 계속 움직인다.
- **feeds 행 수**: `count(*)` 는 2,200만 행을 다 읽는다. 시드 때 센 값에 앱이 넣은 행 수를 더해서 보여준다.
- **도착 배지**: 브라우저 시계가 아니라 서버가 응답에 실어 준 `serverNowMs` 로 계산한다 (Docker VM 시계는 맥과 어긋날 수 있다).

## 배경지식 (시작 전에 모르는 사람이 있으면)

맨 뒤 세 장. 시작 전에 "인덱스 왜 빨라지는지 설명할 수 있는 분?", "커넥션 풀 들어 본 분?" 을 묻고, 약하면 주소 뒤에 `#36` 을 붙여 바로 가서 설명한 뒤 `#1` 로 돌아온다.
- 36 인덱스: 같은 글 16개. 인덱스 없이는 16개 전부 확인, (author_id, created_at) 인덱스는 반씩 좁혀 3번 만에 도착 후 3개만 읽기. 300만 행이면 300만 번 대 약 22번. 대신 쓸 때 인덱스도 고친다.
- 37 두 컬럼 인덱스: 앞 컬럼 순서로 줄 선다. "작성자 7 최신 3개" 는 작성자 먼저 인덱스가, "전체 최신 3개" 는 시간 먼저 인덱스가 빠르다. 부록 34~35 와 이어진다.
- 38 커넥션 풀: 연결 4개짜리 그림이 실제로 돈다. 한 번 넘기면 초당 2.5개(여유), 두 번 넘기면 초당 9개(줄이 쌓이고 3초 넘으면 포기). v1 시연의 빨간 20칸이 이것.
