지연이 아니라 다른 곳으로 갔다

결국빨간 칸은 없어졌다. 하지만 공짜는 아니었다

그림은 축소판이다. 작성자 200명, 오른쪽 한 칸이 글 하나, 옅은 색이 내가 팔로우한 사람. 양쪽이 같은 속도로 읽는다.

① 작성자별 인덱스 + LATERAL 지금 v1

들어간 작성자 0 · 읽은 글 0
-- 작성자마다 최신순으로 줄 선 인덱스
INDEX posts (author_id, created_at DESC)
FROM follows f JOIN LATERAL (
  … WHERE author_id = f.followee_id
  ORDER BY created_at DESC LIMIT 20 ) …

② 시간순 인덱스 + EXISTS 최신 글부터 훑기

훑은 글 0 · 찾은 글 0 / 20
-- 전체 글이 최신순으로 줄 선 인덱스
INDEX posts (created_at DESC, author_id)
FROM posts p WHERE EXISTS ( … follower_id = me
  AND followee_id = p.author_id )
ORDER BY created_at DESC LIMIT 20

① 작성자별 + LATERAL (지금 v1)
② 시간순 인덱스

① 의 비용 ∝ 내 팔로우 수

팔로우가 많은 소수가 느리다. 서비스 전체 규모와는 무관하다.

② 의 비용 ∝ 전체 글 수 ÷ 내 팔로우 수

팔로우가 적은 다수(라이트 70%)가 느리다. 서비스가 커질수록 더 느려진다.

인덱스: 미리 정렬해 둔 찾아보기

찾을 것: 작성자 7 의 최신 글 3개

인덱스 없이 · posts 테이블

글을 쓴 순서대로 쌓여 있다. 한 칸 = 글 하나 (위: 글 번호, 가운데: 작성자, 아래: 시각)16개 전부 확인

인덱스 (author_id, created_at DESC)

작성자별로 줄 세우고, 같은 작성자 안에서는 최신순. 아래 → 는 테이블의 글 번호3번 건너뛰고 3개만 읽기

행이 300만 개라면

인덱스 없이: 300만 번 확인. 인덱스로: 반씩 좁혀서 약 22번 만에 도착 + 필요한 만큼만 읽기

대신 쓰기가 비싸진다

글을 쓸 때마다 인덱스에도 정렬된 자리를 찾아 끼워 넣는다. feeds 는 인덱스가 2개라 한 줄 쓸 때 세 군데를 고친다.
